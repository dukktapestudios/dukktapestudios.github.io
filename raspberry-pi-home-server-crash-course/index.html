Guide

Raspberry Pi Home Server Crash Course

Turn a small, quiet Raspberry Pi 5 into a home server that saves your pictures, hosts a simple website, and stores your movies. Five stages, written for a first-timer. Each stage is useful on its own, so you can stop after any of them.

A learning guide, not a shopping list. Every name, address, and password here is a placeholder: youruser, homeserver, example.com, 192.168.1.50. Swap in your own, and never post your real tokens, keys, or home IP address anywhere public. Prices are as of November 13, 2026, in US dollars, before tax and shipping, and they change. Times are rough estimates for a first-timer.

01What a home server can do

A server is just a computer that stays on and answers requests from other devices. A Raspberry Pi 5 is a credit-card-sized computer that sips power, makes almost no noise, and is more than strong enough for the jobs below.

Save pictures

Keep your photos on a drive you own, in your home, instead of only on a phone or a company's cloud. Stage 5 sets up the storage.

Host a website

Serve a simple site to the whole internet from your living room, with a real https:// padlock. Stage 4 does this with a program called Caddy.

Store movies

Keep home videos and movies you own in one place and watch them around the house. Stage 5 sets up the folder. See the rights note below.

Learn real skills

SSH, firewalls, DNS, and certificates are the same ideas big servers use. A Pi is a cheap, low-risk place to learn them.

Honest tip: you may not need a server for a website. If all you want is a static website (pages and pictures that do not change by themselves), GitHub Pages is simpler and free. There is no hardware, no router settings, and no security patching on your side. A Pi website is worth it when you want to learn, to run things GitHub Pages cannot, or to keep everything under your own roof.

Stage 1Unbox, flash, and connect

Goal: a Pi running Raspberry Pi OS Lite (64-bit) that you can reach from your computer with SSH. Lite has no desktop. That is on purpose: a server runs from the command line, and Lite uses less memory. Time: about an hour.

1.1 Put it together

  1. Unbox the Pi 5 and the case. Clip the board into the case following the sheet in the box, and plug the case fan's cable into the Pi's fan connector.
  2. Leave the microSD card out for now. You will fill it on your computer first.
  3. Put the Pi near your router. Plan to connect it with an Ethernet cable.

1.2 Make an SSH key on your computer

An SSH key is a pair of files that work like a lock and a key. The public file (ends in .pub) goes on the Pi. The private file never leaves your computer and should never be shared. This is far safer than a password. Open a terminal on your own computer (not the Pi) and run:

Windows 10 or 11 (PowerShell)

ssh-keygen -t ed25519 -C "pi-home-server"
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub

macOS (Terminal)

ssh-keygen -t ed25519 -C "pi-home-server"
cat ~/.ssh/id_ed25519.pub

Linux (any terminal)

ssh-keygen -t ed25519 -C "pi-home-server"
cat ~/.ssh/id_ed25519.pub
  • When asked where to save, press Enter to keep the default.
  • When asked for a passphrase, choose one. It protects the key if your computer is ever stolen.
  • The -C text is only a label. Do not put your real name or email in it.
  • The last command prints one line starting with ssh-ed25519. That line is your public key. Copy it.

Raspberry Pi's SSH page suggests Ed25519 keys as a more secure option than the older RSA default.

1.3 Flash the memory card with Raspberry Pi Imager

  1. Download and install Raspberry Pi Imager from raspberrypi.com/software. Put the microSD card in your computer.
  2. Device: choose Raspberry Pi 5.
  3. OS: choose Raspberry Pi OS (other), then Raspberry Pi OS Lite (64-bit).
  4. Storage: choose your microSD card. Check the size so you do not pick the wrong drive, and leave “Exclude system drives” on.
  5. Customisation: fill in each tab. Imager's menu names change a little between versions, but these are the settings to look for:
    • Hostname: homeserver. Letters, numbers, and hyphens only. The Pi will answer to homeserver.local on your network.
    • Localisation: pick your capital city so the time zone, keyboard, and Wi-Fi region are right.
    • User: a username such as youruser and a long, unique password. You still need this password for sudo commands, even after SSH uses keys.
    • Wi-Fi: skip it if you will use Ethernet. If you must use Wi-Fi, enter it now, because a headless Pi needs it the moment it boots.
    • Remote Access: turn on Enable SSH, choose Use public key authentication, and paste the public key line you copied.
  6. Write the card. Wait for Imager to finish and say it is safe to remove the card.

1.4 Boot and connect

  1. Put the card in the Pi, plug in the Ethernet cable, then plug in the power. It starts on its own. The first boot takes a minute or two (my estimate).
  2. On your computer, connect with: 
    ssh youruser@homeserver.local
  3. The first time, SSH asks whether to trust the new machine. Type yes. If you set a passphrase on your key, you will enter it here.
  4. You are in when the prompt changes to youruser@homeserver:~ $. Check that it is 64-bit: 
    uname -m
    It should print aarch64.

Name not found? Wait another minute, then check that the Ethernet light is on. Open your router's “connected devices” page, find the new device named homeserver, and connect with its address instead, for example ssh youruser@192.168.1.50. See the troubleshooting section for more.

Done when: you can type ssh youruser@homeserver.local and get a prompt without typing the account password.

Stage 2Lock it down

Goal: before anything touches the internet, close the easy doors. You will update the system, switch off password and root logins, add a firewall, ban guessers, and turn on automatic security updates. Time: 30 to 45 minutes. Run these on the Pi, over SSH.

2.1 Update everything

sudo apt update
sudo apt full-upgrade
sudo reboot

Say yes when asked. The reboot disconnects you. Wait a minute and SSH back in.

2.2 Confirm key login works

Before you turn passwords off, prove the key works. On your computer, run this. It refuses to fall back to a password, so success means the key is good:

ssh -o PasswordAuthentication=no youruser@homeserver.local

If it logs in (it may ask for your key passphrase, which is fine), carry on. If it says Permission denied (publickey), stop and fix that first. See the troubleshooting section.

2.3 Turn off password login and root login

Keep your current SSH window open while you test. If you make a mistake and close it, you could lock yourself out. Do the change in this window, then open a second window to test. Only close the first window after the second one works.

Modern Debian reads small files from /etc/ssh/sshd_config.d/ before the main file, and the first value it sees for a setting wins. A small file with a name that sorts early is the tidy way to override the defaults. Create one:

sudo nano /etc/ssh/sshd_config.d/01-hardening.conf

Put these lines in it, then save (Ctrl+O, Enter) and exit (Ctrl+X):

PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no

Check the settings for mistakes, then see what SSH will actually use, then restart it:

sudo sshd -t
sudo sshd -T | grep -Ei 'passwordauthentication|kbdinteractiveauthentication|permitrootlogin'
sudo systemctl restart ssh
  • sudo sshd -t prints nothing if the file is fine.
  • The second command should show passwordauthentication no, kbdinteractiveauthentication no, and permitrootlogin no. If it shows yes, another file is winning. Run ls /etc/ssh/sshd_config.d/ and look for a file that sets the same option.

Now, in a new window on your computer, run ssh youruser@homeserver.local. It should still log you in. To prove passwords are off, try ssh -o PubkeyAuthentication=no youruser@homeserver.local. It should be refused. To undo everything, delete the file and restart SSH.

2.4 Turn on the firewall (ufw)

A firewall blocks every connection you did not invite. Allow SSH first, or you will cut your own connection when you enable it.

sudo apt install ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

Port 22 is SSH, 80 is plain web traffic, and 443 is secure web traffic. Some systems also offer sudo ufw allow OpenSSH as a shortcut for the first rule. Optionally add sudo ufw allow 443/udp so browsers can use the newer HTTP/3 with Caddy. If you plan to use a Cloudflare Tunnel in Stage 4, ports 80 and 443 do not need to be open to the internet. The tunnel dials out from the Pi.

2.5 Ban password guessers (fail2ban)

Fail2ban watches the logs and blocks addresses that keep failing to log in. Raspberry Pi OS keeps its logs in the systemd journal instead of a log file, so tell fail2ban to read the journal with backend = systemd.

sudo apt install fail2ban
sudo nano /etc/fail2ban/jail.local

Put this in jail.local. The ignoreip line keeps your own home network from ever being banned. Use your own network range:

[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 192.168.1.0/24
bantime  = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
backend = systemd
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

The last command should list the sshd jail with a count of banned addresses (probably 0 for now).

2.6 Automatic security updates

sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

Choose Yes when it asks whether to automatically download and install stable updates. To rehearse without changing anything, run sudo unattended-upgrade --dry-run -d. By default it installs security fixes, not new features, so it is a safety net and not a replacement for running sudo apt update && sudo apt full-upgrade yourself every month or so.

Done when: you can log in with your key, a password login is refused, sudo ufw status shows the firewall active, and fail2ban-client status sshd works.

Stage 3A fixed address and a name

Goal: the Pi always has the same address on your home network, so your router can send visitors to the right machine. Time: 15 minutes.

3.1 Reserve an address on the router (DHCP reservation)

Your router hands out addresses automatically (that is DHCP) and may give the Pi a different one after a restart. A DHCP reservation tells the router to always give this Pi the same address. It is safer than setting a fixed address on the Pi itself, because the router stays in charge and cannot hand the same address to two devices. Menu names vary by brand, so these steps are general:

  1. On the Pi, note its current address and its hardware (MAC) address: 
    hostname -I
ip -br link
    The MAC address looks like aa:bb:cc:xx:xx:xx and is listed next to eth0 for a cabled connection. Wi-Fi has a different MAC address, so reserve the one you actually use.
  2. Open your router's admin page in a browser. The address and the login are usually on a sticker on the router. Common addresses are 192.168.1.1 and 192.168.0.1.
  3. Find a section named something like DHCP reservation, Address reservation, Static lease, or Fixed IP.
  4. Add a new entry. Pick homeserver from the list of connected devices, or type its MAC address. Choose an address, for example 192.168.1.50. Pick one that the router's automatic range does not use, which is shown on the same DHCP settings page.
  5. Save. Restart the Pi with sudo reboot, then run hostname -I again to confirm it shows the reserved address.

Raspberry Pi OS uses NetworkManager, so the Pi itself needs no settings change. The router does all the work.

3.2 Check or change the hostname

You set the hostname in Imager. To check it, or to change it later:

hostnamectl
sudo raspi-config

In raspi-config, go to System Options, then Hostname, and type the new name. A hostname can use only letters, numbers, and hyphens. This route also updates the Pi's /etc/hosts file for you. The one-line alternative is sudo hostnamectl set-hostname newname, but then you should also edit the 127.0.1.1 line in /etc/hosts to match. Reboot afterwards, and use the new name: ssh youruser@newname.local.

Done when: after a reboot, hostname -I still shows your reserved address and ssh youruser@homeserver.local still works.

Stage 4Your first service: a website

Goal: serve a web page from the Pi at a real address, with HTTPS. We use Caddy, a web server that gets and renews its own free certificates. Time: 1 to 2 hours, mostly waiting on DNS and the router.

Read this first. Putting a server on the internet means strangers will knock on it all day. Serve only a simple static site, keep the Pi updated (Stage 2), never forward port 22 (SSH) on your router, and do not put admin pages or private files behind these ports. If that sounds like more than you want, GitHub Pages is the simpler choice.

4.1 Install Caddy from its official repository

These are the exact commands from the Debian, Ubuntu, Raspbian section of the Caddy install page. Caddy's page is the source of truth, so if the two ever differ, follow theirs.

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install caddy

The package starts Caddy as a background service called caddy. Check it, then visit http://homeserver.local from a computer on your network. You should see Caddy's welcome page.

systemctl status caddy

4.2 Make a page to serve

sudo mkdir -p /var/www/html
echo '<h1>Hello from my Pi</h1>' | sudo tee /var/www/html/index.html
sudo chown -R youruser:youruser /var/www/html

The chown lets you edit the site without sudo. Caddy only needs to read these files.

4.3 Pick a name: free DuckDNS or a paid domain

Visitors type a name, not a number. You need a name that points at your home's public internet address. There are two common routes:

Free name or your own domain
OptionCostGood forWatch out for
DuckDNS Free Learning. You get a name like yourname.duckdns.org and keep it updated when your home address changes. You do not own the name, and it ends in .duckdns.org. It is a free service with no guarantees. It cannot be used with Cloudflare Tunnel, which needs a domain on Cloudflare.
A paid domain Roughly $10 to $20 per year (an estimate; it varies by ending and registrar, and renewals can cost more) A name that is yours, looks professional, and works with Cloudflare Tunnel. A yearly bill. If your home address changes, you still need a way to keep the name pointed at it.

If you choose DuckDNS

  1. Go to duckdns.org, sign in, and type a subdomain name (for example yourname) to add it. Copy your token, a long code shown at the top of the page. Treat it like a password. Anyone with it can change your name's address.
  2. Make a small update script on the Pi. This follows the “linux cron” steps on DuckDNS's install page, with placeholders: 
    mkdir -p ~/duckdns
nano ~/duckdns/duck.sh
    Put this single line in the file, replacing the two placeholders. Use only the subdomain part (yourname, not yourname.duckdns.org), and leave ip= empty so DuckDNS detects your address: 
    echo url="https://www.duckdns.org/update?domains=YOURSUBDOMAIN&token=YOUR-TOKEN&ip=" | curl -s -o ~/duckdns/duck.log -K -
    DuckDNS's own example uses curl -k, which skips certificate checks. This version leaves -k out so the connection is verified.
  3. Make it runnable, test it, and read the log. It should say OK: 
    chmod 700 ~/duckdns/duck.sh
~/duckdns/duck.sh
cat ~/duckdns/duck.log
  4. Run it every 5 minutes with cron. Open the schedule with crontab -e (choose nano if asked) and add this line at the bottom: 
    */5 * * * * ~/duckdns/duck.sh >/dev/null 2>&1
    If crontab is “not found”, install it first with sudo apt install cron.

If you choose a paid domain

Buy the domain from a registrar you trust, then use its DNS settings to create an A record that points your name (for example example.com) at your home's public address. If that address changes, you need dynamic DNS. One simple trick is to point a subdomain such as www at your DuckDNS name with a CNAME record. If you plan to use a Cloudflare Tunnel, you do not need an A record. You add the domain to Cloudflare instead (see 4.6).

4.4 Tell Caddy about your site

Caddy's settings live in /etc/caddy/Caddyfile. Replace everything in it. The one site address line is all it takes to turn on automatic HTTPS:

sudo nano /etc/caddy/Caddyfile
example.com {
    encode zstd gzip
    root * /var/www/html
    file_server
}

Use your own name in place of example.com (for DuckDNS, yourname.duckdns.org). Check the file, then tell Caddy to reload it:

caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy

Caddy now tries to get a free certificate from a public certificate authority, which only works once the name points at your home and ports 80 and 443 reach the Pi (next steps). Until then you will see errors in journalctl -u caddy --no-pager. That is normal. Fix the DNS and router steps and Caddy retries on its own. Do not keep restarting it, because certificate authorities limit how many failed attempts you can make.

4.5 Forward ports 80 and 443 on the router

  1. Open your router's admin page again and find Port forwarding (also called Virtual server or NAT).
  2. Add a rule: external TCP port 80 to the Pi's reserved address 192.168.1.50, port 80.
  3. Add a second rule: external TCP port 443 to 192.168.1.50, port 443.
  4. Do not forward port 22. You can reach SSH from inside your home, which is all you need.

4.6 Check for CGNAT before you blame yourself

Some internet providers put many homes behind one shared public address. This is called CGNAT (carrier-grade NAT), and port forwarding cannot work behind it, because the public address is not really yours.

  1. Open your router's status page and find the Internet or WAN address.
  2. On any device, open a “what's my IP” website and note the address it shows.
  3. If the two addresses match, you have a normal public address. Carry on to 4.8.
  4. If they differ, or the router's address starts with 100.64 to 100.127 (a range reserved for CGNAT, see RFC 6598) or is a private address such as 10.x.x.x, 172.16.x.x to 172.31.x.x, or 192.168.x.x, you are probably behind CGNAT. Use the Cloudflare Tunnel in 4.7. You can also ask your provider about a public address, which may cost extra.

4.7 Only if you are behind CGNAT: a Cloudflare Tunnel

A tunnel makes the Pi dial out to Cloudflare, and Cloudflare brings visitors in through that connection. No port forwarding is needed. You need a domain that has been added to Cloudflare (a free account works, and DuckDNS names cannot be used). The steps below summarize Cloudflare's Create a tunnel (dashboard) guide. Use theirs if the menus have changed.

  1. Log in to the Cloudflare dashboard, go to Networking > Tunnels, and select Create a tunnel. Name it, for example homeserver.
  2. Choose the operating system Debian and the arm64 architecture (the Pi 5 running 64-bit Raspberry Pi OS). The dashboard shows an install command for cloudflared. Copy it and run it on the Pi over SSH. That command contains a secret token, so do not share it or paste it anywhere public.
  3. Wait until the dashboard says the tunnel is connected, then add a published application route: enter a subdomain, pick your domain, and set the Service URL to http://localhost:80.
  4. Cloudflare handles HTTPS for visitors, so tell Caddy to serve plain HTTP on the Pi. Replace the Caddyfile from 4.4 with: 
    :80 {
    root * /var/www/html
    file_server
}
    Then run sudo systemctl reload caddy.

Keep movies and big photo albums off the tunnel. On Cloudflare's Free, Pro, and Business plans, public tunnel addresses may not be used to serve video or a disproportionate amount of large files unless you use a paid Cloudflare service, and Cloudflare can restrict your content if you do. A small website is fine. Watch movies and browse your photo library on your home network, or through a private connection such as the VPN approach in the Home Lab Crash Course.

4.8 Check it from outside your home network

Testing from inside your house can fool you, because your router may not loop traffic back correctly. Test the way a stranger would:

  1. Take your phone, turn Wi-Fi off so it uses mobile data, and open https://example.com (your real name). You should see your page and a padlock.
  2. Or, from a computer on a different network, run: 
    curl -I https://example.com
    A good answer starts with HTTP/2 200 (or HTTP/1.1 200) and includes a line like server: Caddy. A certificate error, or no answer at all, means one of the earlier steps is not done. See the troubleshooting section.

Done when: your page loads over https:// from your phone on mobile data.

Stage 5Add storage

Goal: a big drive, mounted at /mnt/storage, that comes back by itself after every reboot, with folders for Pictures and Movies. Time: 30 to 45 minutes.

5.1 Choose a drive

USB SSD (easiest)

  • Plug it into a blue USB 3 port on the Pi.
  • No extra parts, and you can move it to another computer later.
  • Shows up as /dev/sda (the name may differ).

M.2 HAT+ with an NVMe SSD

  • Faster. It attaches under the Pi through its PCIe connector.
  • Power the Pi off first. Raspberry Pi says to always disconnect power before adding or removing a device in the M.2 slot.
  • Update the Pi's firmware first, as the official page directs: sudo rpi-eeprom-update, then sudo rpi-eeprom-update -a if an update is available, followed by a reboot.
  • After installing it, check that the Pi sees the drive with ls -l /dev/nvme*. You should see /dev/nvme0 and /dev/nvme0n1.
  • The link is a single PCIe 2.0 lane, which Raspberry Pi lists at about 500 MB/s peak. A faster “Gen 3” mode exists but is not certified and may be unstable. Skip it for a first build.

Raspberry Pi OS Lite does not automount drives, which is why the steps below mount it by hand. A brand-new drive also will not show a partition ID in blkid until it has been partitioned and formatted. Both are covered below.

5.2 Find the drive

lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,MODEL,MOUNTPOINTS

Match the size and model to the drive you just plugged in. A USB SSD is usually sda, an NVMe drive is nvme0n1, and your boot card is mmcblk0. In the examples below the drive is /dev/sda. If yours is nvme0n1, its first partition is called /dev/nvme0n1p1 (with a p).

5.3 Format it (ext4)

This erases the drive. Every file on the drive you name below is destroyed and cannot be recovered. Copy anything you want to keep somewhere else first. Triple-check the device name against lsblk. Never run these commands on mmcblk0. That is the Pi's own memory card with your operating system on it.

sudo parted /dev/sda --script mklabel gpt mkpart storage ext4 0% 100%
sudo mkfs.ext4 -L storage /dev/sda1

The first command makes a fresh partition table with one partition that fills the drive. The second formats that partition as ext4, the standard Linux filesystem, and labels it storage. If parted is missing, run sudo apt install parted.

5.4 Mount it by hand once

sudo mkdir -p /mnt/storage
sudo mount /dev/sda1 /mnt/storage
df -h /mnt/storage

df should show the drive's size. If it does, the format and mount work.

5.5 Make it mount at every boot (fstab)

The file /etc/fstab lists the drives to mount at startup. Use the drive's UUID, which never changes, instead of sda1, which can change.

sudo blkid /dev/sda1

Copy the long value after UUID= (it looks like 1b2c3d4e-0000-4aaa-bbbb-1234567890ab; that one is made up). Back up fstab, then open it:

sudo cp /etc/fstab /etc/fstab.bak
sudo nano /etc/fstab

Add this line at the bottom, with your own UUID:

UUID=1b2c3d4e-0000-4aaa-bbbb-1234567890ab  /mnt/storage  ext4  defaults,nofail,x-systemd.device-timeout=30  0  2
  • nofail lets the Pi boot normally even if the drive is unplugged or fails.
  • x-systemd.device-timeout=30 makes the Pi wait 30 seconds, not the default 90, for a missing drive.

Now test it before you reboot. A typo in fstab can cause boot trouble, so find mistakes now:

sudo systemctl daemon-reload
sudo umount /mnt/storage
sudo mount -a
df -h /mnt/storage

If mount -a prints nothing and df shows your drive again, the line is right. If it prints an error, fix the line, or restore your backup with sudo cp /etc/fstab.bak /etc/fstab. Finally, run sudo reboot, log back in, and run df -h /mnt/storage once more to prove it came back by itself.

5.6 Make folders for Pictures and Movies

sudo chown youruser:youruser /mnt/storage
mkdir -p /mnt/storage/Pictures /mnt/storage/Movies

Now /mnt/storage/Pictures and /mnt/storage/Movies belong to you. Copy files in with scp or rsync from your computer, for example scp -r ~/Pictures/2026 youruser@homeserver.local:/mnt/storage/Pictures/.

One drive is not a backup. If the drive dies, or you erase it by mistake, the files are gone. Keep a second copy of anything you cannot replace, such as family photos, on another drive or a service you trust.

5.7 Where to go next

  • Share the drive on your home network with Samba, so Windows, Mac, and phones can open it like a folder. Raspberry Pi's Samba section is a good start. Share only inside your home. Do not forward Samba to the internet.
  • A photo app such as Immich or PhotoPrism gives you a phone-friendly gallery. Both are bigger projects. Check each one's requirements and setup guide before you commit.

Done when: after a reboot, df -h /mnt/storage shows the drive and you can copy a file into Pictures.

Please readHost only what you have the right to host

Host only content you own or have the rights to share. That means your own photos, home videos, writing, and music, and files whose license lets you share them. Do not host pirated movies, shows, music, or software. It is illegal in most places, it can get your internet service cut off, and a public server is easy to trace back to you. Rules about copying discs you own for private use differ by country. This guide is not legal advice, so check the rules where you live. Keep your movie library private on your home network.

HelpTroubleshooting and FAQ

ssh: Could not resolve hostname homeserver.local

Give the Pi another minute to finish its first boot and check the Ethernet light. Look for the Pi in your router's connected-devices list and use its address instead (ssh youruser@192.168.1.50). Some Windows and corporate networks do not support .local names, so the address is the reliable fallback. Raspberry Pi's find your IP address section lists more ways.

Permission denied (publickey)

The Pi does not have the public key your computer is offering. Check that you pasted the line from the .pub file (not the private one) into Imager. Run ssh -v youruser@homeserver.local to see which key it tries. If it will not work, the quickest fix before the Pi holds anything important is to re-flash the card with the right key.

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

This appears after you re-flash the card, because the Pi is a “new” machine with the old name. If you know you re-flashed it, clear the old entry with ssh-keygen -R homeserver.local and try again.

I locked myself out after the hardening step.

This is why Stage 2 says to keep one session open. If you still have it, delete /etc/ssh/sshd_config.d/01-hardening.conf, run sudo systemctl restart ssh, and try again. If you have no session left, plug a keyboard and monitor into the Pi and log in at the console, or re-flash the card.

Caddy cannot get a certificate, or https:// does not load.

Run journalctl -u caddy --no-pager -n 50 and read the last lines. Then check each link in the chain:

  • Does the name point at your home address? Compare the address nslookup example.com shows with the address a “what's my IP” site shows. For DuckDNS, check that ~/duckdns/duck.log says OK.
  • Are ports 80 and 443 forwarded to the Pi's reserved address, and does sudo ufw status allow them?
  • Are you behind CGNAT? See 4.6, then use the tunnel.
  • Some providers block incoming port 80 on home plans. Ask your provider, or use a Cloudflare Tunnel.

It works on my phone's mobile data but not from my home Wi-Fi.

Some routers cannot loop a request for your own public address back inside the house (NAT loopback). The site is working. Test from outside, as in 4.8.

My home address changed and the site went down.

Home addresses are not permanent. For DuckDNS, check that the cron job is in place with crontab -l and that duck.log says OK. For a paid domain, set up dynamic DNS as in 4.3.

The drive is missing after a reboot.

Run lsblk to see if the Pi sees it. Try sudo mount -a and read any error. Check the UUID in /etc/fstab against sudo blkid, and reseat the cable. Because of nofail, the Pi boots even when the drive is absent.

Files went onto the memory card instead of the drive.

If the drive was not mounted, anything written to /mnt/storage landed on the card. Run findmnt /mnt/storage before copying big files. It prints a line only if the drive is mounted.

How do I turn it off safely?

Run sudo shutdown -h now, wait for the lights to settle, then unplug the power. Pulling the plug while it is running can corrupt the memory card.

How do I keep it updated?

Run sudo apt update && sudo apt full-upgrade about once a month and reboot if it asks. Unattended upgrades covers security fixes in between.

I got stuck on the firewall. How do I turn it off?

Run sudo ufw disable to switch it off, and sudo ufw status numbered to see the rules. Re-enable it with sudo ufw enable once SSH (port 22) is allowed again.
