01Start here: the one big idea

A connected system is a few small programs, each with one job, passing data to each other through agreed messages. A website alone shows things. A system notices something, stores it, does work on it later, and tells a person or another program what happened.

Remember this shape. Almost every example on this page is this five-box pattern with different labels. Learn it once with the starter project, then reuse it.

Terms used on this page
TermMeaning
APIApplication Programming Interface: a set of URLs another program can call to ask for data or an action.
Source of truthThe one place whose answer wins when two copies disagree. Usually the database.
WorkerA program that runs separately from the API and does slow jobs (resize images, call AI) so the user isn't waiting.
ContractThe agreed shape of a message, e.g. which JSON fields exist and what they mean.

02Minimum path

Learn in this order. Each step adds one new piece to something that already works.

  1. Script + file — A Python script reads a folder and writes a JSON report. One program, no network.
  2. API + database — A small FastAPI server saves and lists records in SQLite. Two pieces talking.
  3. Add a worker — Slow work moves to a background process that claims jobs from the database. Three pieces.
  4. Dashboard — A web page shows job status by calling the API. Now it is a system you can watch.
  5. One outside service — Add exactly one: an AI API, a webhook from another app, or MQTT from a device.
  6. Deploy and protect — Git, secrets in environment variables, logs, a backup, then host it.

Recommended starter stack: Python, FastAPI, SQLite, a plain HTML or simple React dashboard, Git. Move to Postgres or a managed backend only when you need several users or a hosted server.

No-code automation vs scripts

Automation tools (n8n, Make, Zapier) — pros

  • Prebuilt connectors to many apps, sign-in handled for you
  • Visual run history makes simple flows easy to debug
  • n8n can be self-hosted (Docker) or used as a cloud service

Watch out for

  • Complex branching gets hard to read and test
  • Plans and limits change; check each vendor's current pricing page
  • Your business rules live in someone else's editor, not in Git

Good split: let an automation tool handle "when a form is submitted, call my API", and keep the actual rules in your own code where you can test them.

04How pieces talk

Ways programs pass messages
MethodPlain meaningUse for
HTTP + JSONAsk a URL, get a structured replyMost app-to-app calls
SDKA library that wraps an API so you call functionsBig services (AI, payments, storage)
WebhookThe other service calls your URL when something happensPayments, form submissions, Git pushes
PollingYou ask every N minutes "anything new?"Services with no webhooks; simple and robust
Queue / job tableLeave a work ticket; a worker picks it upSlow or retryable work
WebSocketA connection that stays open both waysLive game state, live dashboards
MQTTLightweight publish/subscribe for devicesSensors, home automation

This is the pattern Stripe's webhook docs describe: verify the signature, return a 2xx quickly, process asynchronously, and expect duplicates and out-of-order delivery.

05Reliability: jobs, retries, duplicates

Things fail: networks drop, APIs time out, workers crash mid-job. A reliable system assumes this and records progress in the database.

Reliability ideas
ConceptMeaning
IdempotencyDoing the same request twice has the same effect as once. Use a unique key (file checksum, event id) and refuse a second insert.
DeduplicationRemember ids you already processed. Webhooks and retries will send repeats.
Retry with backoffWait longer each time (e.g. 10s, 1m, 5m) so you don't hammer a struggling service.
TimeoutNever wait forever on a call. Give each outside call a limit, then fail and retry.
Dead letterWhere jobs go after too many failures, with the error saved, for a person to inspect.
Lease / heartbeatA running job records when it was claimed; if a worker dies, another can reclaim after a deadline.
ScheduleTimed jobs (cron) for cleanups and polling. Keep them idempotent too.

06AI pieces, agents, and MCP

Treat AI as one worker step with a strict contract, not as the boss of the system.

AI patterns
PatternWhat it isUse when
Single callText in, text outDrafts, summaries, rewording
Structured outputModel must return JSON matching a schemaAnything your code reads next; validate it anyway
RAGLook up your own documents, paste relevant parts into the promptAnswers grounded in your notes, rules, or catalog
Tool useModel asks your code to run a named functionLookups and safe actions you define
AgentModel loops: plan, call tools, check, repeatOpen-ended tasks where steps are unknown
Deterministic workflowYour code fixes the steps; AI fills oneMost business pipelines; easier to test and audit
Local modelRuns on your machine (e.g. via Ollama)Privacy, offline, no per-call fee; needs a capable GPU/CPU

MCP is a plug, not a brain. The Model Context Protocol is an open standard for connecting AI apps to data and tools through MCP servers. It standardizes how a tool is described and called. It does not decide your workflow, add reliability, or make an action safe; your server's permissions and your approval rules still do that.

Rule of thumb: if anyone besides you depends on it, it should not live on a computer that sleeps.

08Security and safety rules

Rules to build in from day one (required practices, not a record of anything set up):

  • Secrets (API keys) live only on the server, in environment variables, never in browser code or Git
  • Validate every input on the server, even if the page already checked it
  • Least privilege: each key and each user can do only what their job needs
  • OAuth for acting on someone's account: they grant scoped access, you never see their password
  • Row-level rules: a user can read only their own rows (e.g. Postgres row-level security)
  • Verify webhook signatures and reject old timestamps
  • Location and personal data: ask consent, collect the minimum, delete when done
  • Human approval before spending money, sending messages, posting, or deleting

09Example systems

Pick an example. Each is a conceptual design, not something running. Default selection on the page: Cards.

Concept designs — not live systems.

Content pipeline

Goal: Turn a raw idea or recording into a reviewed Dukktape Studios post draft, never auto-posted.

Source of truth
The database row for each piece of content. The AI output is a suggestion stored as a draft, never the final word.
Cost
AI calls are billed per use by most providers; batch small drafts and cap retries so one stuck job cannot loop.
Failure
AI returns malformed text → validate against a schema, mark the job failed, keep the raw input for retry.
Privacy
Keep unpublished drafts private; do not send other people's personal info to an AI API without need.
Human approval
Posting is irreversible and public, so a person approves every post. Automation stops at draft.
First version
One form, one table, one worker that writes a fake draft. Swap in the AI call last.

Card asset pipeline

Goal: Upload Hoofprint card art once, process it in the background, catalog it, and expose it to a shop later (concept only).

Source of truth
Catalog database for card identity and status; object storage only holds bytes. A file checksum prevents duplicate cards.
Cost
Storage and bandwidth grow with image size; keep originals once and generate small previews.
Failure
Corrupt or wrong-size upload → job fails with a readable reason; the original is kept, nothing reaches the shop.
Privacy
Unreleased art stays in private storage; previews can be public only after approval.
Human approval
Listing a product, changing a price, or sending files to a printer each need a person's approval.
First version
This is the starter project below. Local folder instead of cloud storage, SQLite instead of Postgres.

PNGtuber avatar

Goal: Mic audio drives a duck avatar's mouth, blink, and mood in real time on one computer.

Source of truth
The in-memory state on the local machine. No server or database is needed.
Cost
Free to run locally; the cost is CPU time, so keep the render loop light.
Failure
Noisy room → mouth flaps constantly. Fix with a threshold plus hold time (hysteresis), not more code paths.
Privacy
Audio never needs to leave the computer. Do not record or upload it.
Human approval
None needed; it changes nothing outside the screen.
First version
A slider for fake loudness first, then the mic. This separates audio bugs from drawing bugs.

Co-op location game

Goal: Players meet at safe public places to fight monsters as tank, healer, and DPS; businesses sponsor optional drops.

Source of truth
The game server decides damage, loot, and rewards. The phone only sends intentions such as "use heal on player 3".
Cost
Realtime servers and map tiles cost more as players grow; start with one area and a capped number of encounters.
Failure
GPS spoofing, lag, a player dropping mid-fight. Server validates speed and distance, holds fight state, allows rejoin.
Privacy
Location consent in plain words, coarse location when possible, never show a player's live or home location to others.
Human approval
Business offers, new spawn spots, and prize redemption are approved by a person. Spots must be public and permitted.
First version
Fake GPS on a desktop web page, one encounter, three roles, server-side combat in memory. Map later.

Home sensor alerts — hypothetical

Hypothetical design only. It does not describe a real building, a real sensor, or anything installed.

Goal: Get a notification if the garage door is open too long or a freezer warms up.

Source of truth
Home Assistant's latest sensor state. The ESP32 only reports; it does not decide.
Cost
Hardware is a one-time cost; something must stay powered on 24/7 (a mini PC or Pi), so plan for power cuts.
Failure
Sensor offline looks like "nothing wrong". Use availability (last will) messages so silence becomes an alert.
Privacy
Keep it on the home network; do not expose the broker to the internet.
Human approval
Alerts are fine automatically; anything that unlocks or opens a door needs a deliberate confirmation.
First version
Simulate the sensor by publishing a test message from a laptop before buying parts.

10Starter project: asset processing system

Goal: drop an image into a local dashboard, have a worker make a thumbnail and checksum in the background, and watch the status change. Uses sample public-domain or your own non-private images. Everything runs on one computer.

This page does not install packages, start a server, or build the project. The steps below are the lesson.

Data contract

Agree on this before writing code. The API returns it; the dashboard and worker both rely on it.

Asset record
FieldTypeMeaning
idintegerAsset id
filenametextOriginal name, for display
sha256text, uniqueChecksum; the idempotency key
statustextqueued, running, done, failed, dead
attemptsintegerHow many times the worker tried
errortext or nullLast failure reason
thumb_pathtext or nullSet when done
updated_attimestampLast change; also used to reclaim stuck jobs

Example reply from GET /assets/7:

{"id":7,"filename":"duck.png","status":"done","attempts":1,"thumb_path":"thumbs/7.png","error":null}

Endpoints

Starter API calls
CallDoesExpected result
GET /healthLiveness check{"ok": true}
POST /assetsUpload file, compute checksum, insert row as queued201 with the asset; 200 with the existing asset if the checksum already exists
GET /assetsList all assets with statusJSON array, newest first
GET /assets/{id}One asset404 if missing
POST /assets/{id}/retryMove a dead asset back to queuedOnly allowed from dead or failed

Build it in order

  1. Set up — New folder, Git repo, Python virtual environment, install fastapi, uvicorn, pillow. Run fastapi dev main.py and open http://127.0.0.1:8000/docs.
  2. Milestone 1: two pieces (API + DB) — Create the assets table on startup. POST /assets inserts, GET /assets lists. Check: upload twice via /docs, list shows one row (checksum is unique).
  3. Milestone 2: three pieces (add worker) — worker.py loops: claim one queued row by setting it to running in a single UPDATE, make a 256px thumbnail, set done. Check: status goes queued → running → done within seconds.
  4. Milestone 3: dashboard — A plain HTML page with a file input and a table that calls GET /assets every 2 seconds. Check: you see status change without refreshing.
  5. Milestone 4: failure test — Upload a .txt renamed to .png. Check: attempts climbs to 3, status becomes dead, error says it cannot read the image, the API keeps working.
  6. Milestone 5: crash test — Stop the worker while a job is running, restart it. Check: rows stuck in running longer than 60s go back to queued and finish.
  7. Milestone 6: duplicate test — Upload the same image three times quickly. Check: still one row and one thumbnail.

Done means: you can explain which piece owns each fact, you watched a job fail safely, and restarting any one piece loses nothing.

12Monolith or separate services?

The chart's horizontal axis runs from few people and parts to many teams and parts. The vertical axis runs from low scale to high scale.

A modular monolith is one codebase and one deployable app, organized into clear folders (assets, jobs, users) that talk through functions. Add a separate worker process early because slow work needs it. Split into separate services only when one part needs different scaling, language, or ownership. Microservices add network failures, deploy complexity, and data consistency problems you do not need yet.

13Debugging checklist

  1. Is each piece running? Check /health, the worker log, the DB file exists.
  2. Follow one record: find its id and check every hop in order.
  3. Read the actual error message and the HTTP status (4xx is your request, 5xx is the server).
  4. Compare the message to the data contract: field names, types, null vs missing.
  5. Reproduce with the smallest input: one file, one request in /docs or curl.
  6. Check time and timeouts: is something waiting forever?
  7. Check config: wrong port, wrong env var, wrong file path, wrong database.
  8. Change one thing, retest, write down what happened.

14Prompts for a coding assistant

  • Scope: "Build only Milestone 2 of my asset system." Use this data contract (paste). Do not change the API routes or the table schema. Show me the files you will change first.
  • Secrets: "Read keys only from environment variables." Never print, log, or commit a key. Add a .env.example with placeholder names only.
  • Tests: "Write a test for each milestone check." Include the duplicate upload, bad file to dead, and stuck running job recovery. Tell me the command to run them.
  • Approval: "Ask before anything irreversible." No deleting files, deploying, sending messages, or spending money without my explicit yes.
  • Explain: "After coding, explain the data flow." Which piece owns each fact, and what happens if each piece crashes.

15Advanced reference
Extra topics, collapsed until you open them
TopicNote
SQLite → PostgresSwitch when several servers or users write at once, or you need hosted backups. Same SQL ideas.
GeospatialPostGIS adds location types and "within distance" queries to Postgres; good for spawn points and approved spots.
GPS spoofingServer checks travel speed between reports, distance to the encounter, and repeated impossible jumps. Treat client location as a claim, not a fact.
Realtime scaleOne encounter = one room/channel. Server holds state and broadcasts; clients send actions only.
Object storageStore files by key, keep originals private, hand out time-limited links when needed.
ObservabilityStructured logs with job id, a few metrics (queue length, failures/hour), and an alert when the dead count rises.
DockerPackages API, worker, and DB into reproducible containers; use when deploying or sharing setup.
CIGitHub Actions runs tests on every push so broken code is caught before deploy.
BackupsA backup you have never restored is a hope. Test a restore once.
